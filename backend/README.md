# Backend (Supabase)

Проект Supabase: `dqeejdtwwwisptkexchj`.

## Схема данных

| Таблица | Назначение |
| --- | --- |
| `profiles` | Профиль пользователя, создаётся автоматически при регистрации (триггер на `auth.users`) |
| `projects` | Проекты водоснабжения, принадлежат пользователю (`owner_id`) |
| `datasets` | Структурированные исходные данные; для каждой пары `(project_id, kind)` хранится одна каноническая строка |
| `buildings` | Здания-потребители: координаты, этажность, жители |
| `nodes` | Узлы сети: источник, узловые точки, гидранты, задвижки, вантузы, выпуски, колодцы |
| `pipes` | Участки сети: узел начала и конца, длина, диаметр, материал |
| `calc_runs` | Запуски гидравлического расчёта: статус, параметры, сводка результатов |
| `exports` | Сгенерированные документы: DXF, PDF, XLSX (файлы лежат в Storage) |

Storage: приватные бакеты `source-files` (исходники) и `exports` (результаты).
Путь файла: `{user_id}/{project_id}/{имя файла}`.

RLS: включён на всех таблицах. Доступ к строкам имеет только владелец проекта
(функция `is_project_owner`). В Storage пользователь видит только свою папку.

## Как применить миграции

Новая установка:

1. Откройте Supabase Dashboard -> SQL Editor -> New query.
2. Выполните `migrations/0000_full_schema.sql` (он заменяет `0001` и `0002`).
3. Затем выполните миграции `0003`–`0015` строго по номеру. Файлы
   идемпотентны, поэтому уже включённые в сводную схему операции безопасно
   повторяются.

Существующая установка: выполните все ещё не применённые миграции по номеру.
`0014_dataset_uniqueness.sql` обязательна для гарантии одной строки dataset
при конкурентном сохранении:
она детерминированно оставляет самую новую строку каждого вида и добавляет
`UNIQUE (project_id, kind)`. Frontend совместим с обеими версиями схемы:
сначала обновляет строки пары, при отсутствии вставляет новую, а конфликт
параллельной вставки `23505` завершает повторным обновлением. До применения
`0014` сама БД всё ещё не может исключить дубликаты от двух одновременных
первых сохранений.

`0015_basis_file_atomic.sql` добавляет owner-scoped RPC `save_basis_file`.
Она с блокировкой строки объединяет один ключ `basis.content.files`, сохраняя
остальные файлы и метаданные даже при параллельных загрузках. До применения
`0015` frontend временно использует совместимое клиентское слияние только при
ответе Supabase об отсутствующей функции; другие ошибки не скрываются.

Каждый SQL-файл должен завершиться без ошибок (`Success. No rows returned`).

## Настройка Auth

Authentication -> Sign In / Providers -> Email: провайдер включён по умолчанию.
Для хакатона отключите Confirm email, иначе регистрация будет требовать
подтверждения по почте, а встроенный SMTP Supabase сильно ограничен по числу писем.
