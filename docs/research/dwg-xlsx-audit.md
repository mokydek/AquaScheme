# Аудит DWG/XLSX-конвейера AquaScheme

Дата проверки: 2026-07-29 (Asia/Yekaterinburg).

## Объём и ограничения проверки

Проверены без изменения исходных файлов:

- `P04` — реальный DWG (локальный файл пользователя);
- `P06` — таблица геологии;
- локальная реализация `converter/`;
- публичные `health`, `ready` и CORS-заголовки production-конвертера;
- production-конфигурация фронтенда по опубликованным JS-ресурсам;
- двусторонняя конвертация на искусственном чертеже без проектных данных.

Реальный DWG не передавался во внешний сервис: это конфиденциальный проектный файл, а публичный endpoint не является достаточным основанием для его выгрузки. MSI ODA не устанавливался и не распаковывался.

## Итог

1. Production-конвертер развёрнут и способен выполнять DWG ↔ DXF: `/health` и `/ready` вернули HTTP 200, а искусственный тест успешно прошёл DXF → DWG → DXF с сохранением слоёв, единиц и координат Z.
2. Production CORS настроен небезопасно: preflight для постороннего `https://example.invalid` получил `Access-Control-Allow-Origin: https://example.invalid`. Это означает, что `ALLOWED_ORIGINS` фактически не ограничивает вызывающие сайты.
3. Текущая production-сборка фронтенда действительно содержит `https://aquascheme.onrender.com` как `VITE_CONVERTER_URL`.
4. Структуру реального DWG (слои, сущности, диапазоны X/Y/Z, систему координат) подтвердить локально пока нельзя: ODA/LibreDWG/Docker отсутствуют, а реальный файл нельзя безопасно выгружать в публичный Render.
5. XLSX не удалось открыть предусмотренным `@oai/artifact-tool`: загрузчик bundled runtime четырежды не завершил работу, включая повторную проверку перед завершением аудита. По правилам табличного инструмента альтернативный парсер не применялся. Поэтому листы, реальные значения, формулы и визуальное состояние данного файла остаются непроверенными. Ниже отдельно зафиксирован контракт, который ожидает код приложения.

## Converter

### Реализация

`converter/src/index.js` предоставляет:

- `GET /health` — жив ли Node-процесс;
- `GET /ready` — найден ли провайдер;
- `POST /convert?to=dwg|dxf&version=ACAD...` — multipart-поле `file`;
- лимит файла 25 MiB;
- допустимые выходные версии `ACAD2000`, `2004`, `2007`, `2010`, `2013`, `2018`;
- passthrough, когда исходный и целевой форматы совпадают.

Рабочий провайдер — ODA. `cloudconvert` объявлен, но `ready()` всегда сообщает, что реализация отсутствует, и `convert()` выбрасывает исключение.

### Production

| Проверка | Результат |
|---|---|
| URL | `https://aquascheme.onrender.com` |
| `/health` | HTTP 200, `ok: true`, provider `oda`, commit `b02df33` |
| `/ready` | HTTP 200, `ok: true`, provider `oda` |
| Встроен во frontend | да, в динамическом модуле страницы проекта |
| Корректный production origin | preflight HTTP 204, origin разрешён |
| Посторонний origin | preflight HTTP 204, **origin также разрешён** |

Следовательно, readiness проверяет лишь наличие исполняемых файлов, но не выполняет контрольную конвертацию.

### Безопасный end-to-end тест

Для теста библиотекой проекта был создан искусственный DXF с:

- единицами `metre` (`$INSUNITS = 6`);
- слоями `AUDIT_ROUTE` и `AUDIT_TOPO`;
- LINE `(100, 200, 351.25) → (120, 210, 350.75)`;
- POINT `(105, 205, 351)`.

Результат:

| Направление | HTTP | Размер | Результат |
|---|---:|---:|---|
| DXF → DWG | 200 | 11 640 байт | DWG `AC1032` |
| DWG → DXF | 200 | 75 030 байт | корректный DXF |

После круговой конвертации подтверждены `$INSUNITS = 6`, оба слоя, обе сущности и все X/Y/Z. Это доказывает работоспособность endpoint на корректном DXF, но не раскрывает содержимое реального DWG.

Отдельный нарочно минимальный/неполный DXF дал HTTP 500 с `ENOENT ... out/drawing.dwg`: ODA завершился без выходного файла, а сервис попытался читать отсутствующий результат. Это выявляет недостаточно ясную диагностику невалидного входа.

### Существенные риски converter

1. **P0 — CORS wildcard.** Production отражает произвольный Origin. Нужно задать точный `ALLOWED_ORIGINS` и проверить production/preview домены.
2. **P0 — нет безопасного локального пути для конфиденциального DWG.** Реальный файл нельзя отправлять в публичный endpoint без отдельного явного решения владельца о допустимости передачи.
3. **P1 — readiness неполный.** `/ready` не выполняет smoke-конвертацию.
4. **P1 — ошибка отсутствующего output.** После exit code 0 следует искать фактический выходной файл и возвращать понятный код вроде `CONVERSION_OUTPUT_MISSING`, а не сырой `ENOENT`.
5. **P1 — нет аутентификации/rate limit.** Endpoint принимает файлы от любого клиента, а при текущем CORS — и от любого сайта.
6. **P2 — определение входного формата слабое.** Любой файл без `.dwg`/`.dxf` и без `AC10` считается DXF; содержимое DXF до запуска ODA не валидируется.

## Что фронтенд и engine извлекают из DXF

`engine/src/dxfread.ts` сейчас обрабатывает:

- `LINE`, `LWPOLYLINE`, `POLYLINE` как сегменты;
- `POINT`, `INSERT` как маркеры;
- слой, тип сущности, handle, цвет, тип линии и до 20 текстовых/блочных примеров на слой;
- `$INSUNITS`;
- предположительное поле `coordinateSystem` только из `$PROJECTNAME` или `$CANNOSCALE`.

Классификатор различает коридор, направляющую ось, красные линии, коммуникации, дороги, железную дорогу, гидрографию, рельеф/breaklines, проектную трассу, здания/сооружения, охранные и запретные зоны, разрешённые пересечения и участки.

### Ограничения парсера, важные для реального DWG

- Z сохраняется только для `POINT`/`INSERT`. Вершины LINE/POLYLINE преобразуются только в `{x, y}`, поэтому 3D-полилинии и Z концов линий теряются после импорта.
- `INSERT` используется как одна точка; содержимое блока не разворачивается. Если топознаки и здания хранятся внутри блоков, геометрия будет неполной.
- ARC, CIRCLE, SPLINE, HATCH, 3DFACE и другие сущности не превращаются в ограничения/рельеф.
- `$PROJECTNAME`/`$CANNOSCALE` не являются надёжным CRS. Для карты всё равно нужны явный proj4/EPSG или контрольные точки.
- Подписи высот, записанные как TEXT/MTEXT без геометрического Z, не преобразуются в точки рельефа.
- Приложение честно считает файл без ненулевых Z у POINT/INSERT файлом без отметок; такой DWG не даст поверхность.

### Блокер инспекции

Предусмотренный `codex_app__load_workspace_dependencies` четырежды не вернул пути bundled Node/runtime и `@oai/artifact-tool` (вызовы оставались в состоянии running и были остановлены после длительного ожидания). В соответствии с правилами spreadsheet skill:

- не использовались `openpyxl`, SheetJS, Excel COM или ручная распаковка XLSX;

Это инструментальный blocker аудита, а не доказательство дефекта самого XLSX.

### Контракт приложения (из кода, не из инспекции данного файла)

Кнопка создания шаблона в `GeologySection.tsx` формирует один лист `Геология`, три демонстрационные строки и 18 колонок:

1. `Скважина`
2. `X`
3. `Y`
4. `Отметка устья, м`
5. `ИГЭ`
6. `Грунт`
7. `Кровля слоя, м`
8. `Подошва слоя, м`
9. `Плотность, г/см3`
10. `Влажность, %`
11. `Угол трения, град`
12. `Сцепление, кПа`
13. `Модуль деформации, МПа`
14. `Коэффициент фильтрации, м/сут`
15. `УГВ, м`
16. `Агрессивность к стали`
17. `Агрессивность к бетону`
18. `Агрессивность к ПЭ`

Импорт читает **только первый лист** (`book.SheetNames[0]`) и превращает его в строки. Парсер:

- группирует строки по названию скважины;
- принимает точку или запятую как десятичный разделитель;
- проверяет обязательность идентификатора скважины;
- проверяет числовые поля;
- требует `Подошва > Кровля`;
- принимает агрессивность `low/medium/high` и русские эквиваленты;
- выбирает минимальную глубину УГВ и максимальную агрессивность для сводки.

Формулы шаблону из кода не добавляются: генератор записывает статические значения. Но наличие или отсутствие формул в предоставленном файле не подтверждено. При импорте приложение не анализирует формулы и их зависимости — оно получает значения первого листа через `sheet_to_json`.

### Что требуется проверить после восстановления bundled runtime

1. Имена и количество листов.
2. Used range каждого листа.
3. Значения и формулы всех заполненных ячеек.
4. Совпадение первого листа с 18-колоночным контрактом.
5. Пустые/скрытые листы, merged cells, фильтры, проверки данных.
6. Ошибки формул `#REF!`, `#VALUE!`, `#NAME?`, `#N/A`, `#DIV/0!`.
7. Визуальный render всех листов и отсутствие обрезанных заголовков.

## Вывод для инженерного конвейера

Сейчас можно утверждать, что общий механизм ODA и production URL работоспособны. Нельзя утверждать, что AquaScheme уже получает из предоставленного реального DWG координаты, отметки и необходимые ограничения: сам файл не был безопасно преобразован, а parser имеет значимые ограничения по 3D-полилиниям, блокам и видам сущностей.

Также нельзя считать геологический XLSX проверенным до успешной read/inspect/render-процедуры через bundled `@oai/artifact-tool`. Код ожидает понятную 18-колоночную схему, но факт соответствия конкретного файла пока не доказан.
