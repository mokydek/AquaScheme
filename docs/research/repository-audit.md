Базовый проверенный commit: `c529d50` (`fix: support legacy node constraints`). Разделы о генераторе и тестовом контуре ниже актуализированы по текущей рабочей копии после аудита.

## Объём и ограничения аудита

Проверены исходники `frontend/`, `engine/`, `converter/`, `backend/`, экспорт, скрипты и документация. Выполнялись только локальные чтения, компиляция и тесты. Production Supabase, Storage, Vercel и Render не изменялись. Существующая неотслеживаемая папка `tmp/` не читалась для анализа продукта, не изменялась и не добавлялась в Git.

В корне проекта отсутствует `AGENTS.md`. Учтены правила из `CLAUDE.md`: конфиденциальный эталон хранится вне Git, нельзя подгонять расчёты под него, Vitest запускается в одном потоке, существенные изменения требуют benchmark.

## Состояние Git

- До аудита: только `?? tmp/`.
- Отслеживаемых пользовательских изменений не было.
- Текущая итерация дополняет аудит реализацией в `engine/`, `frontend/`, `converter/`, тестовыми скриптами и файлами `docs/research/`; приватные исходники и артефакты сравнения остаются вне Git.
- `dist/` после production-сборки не попал в Git, потому что каталог игнорируется.

## Архитектура

| Область | Реализация | Наблюдение |
| --- | --- | --- |
| Корень | npm workspaces | В workspace входят только `frontend` и `engine`; `converter` устанавливается и запускается отдельно. |
| Frontend | React 19, TypeScript, Vite 7, React Router, Supabase, Leaflet, pdfjs, pdfmake, XLSX | Рабочее SPA с авторизацией, проектами, импортом, расчётами, картой и экспортом. Тяжёлые модули и Web Workers загружаются динамически. |
| Engine | чистый TypeScript | Расходы, трассировка, EPANET, Manning, профили, геология, нормы, материалы, DXF и реестр рабочих листов. |
| Backend | SQL-миграции Supabase | Таблицы, RLS, приватный Storage и проектные RPC. Автоматического migration runner/CI в репозитории нет. |
| Converter | Express + ODA File Converter | Двусторонний DWG↔DXF HTTP-сервис, работоспособность зависит от отдельной установки ODA. |
| Export | DXF, PDF, XLSX, ZIP; DWG через converter | Экспорт генерируется из расчётной модели. Финальные рабочие листы блокируются по статусам источников. |
| Deploy | Vercel frontend; Render/Docker converter | `vercel.json` настроен. Backend и converter требуют отдельных ручных шагов. |

Документация расходится с кодом карты: `README.md` и `docs/PHASES.md` называют MapLibre, но текущая реализация и зависимости используют Leaflet (`frontend/src/app/project/LiveSituationMap.tsx`).

## Что уже является настоящей реализацией

1. **Данные и безопасность.** Supabase-клиент использует публичные frontend-переменные, строки проектов защищены RLS, Storage — приватными bucket и политикой пути пользователя. RPC `replace_project_network` проверяет владельца проекта и заменяет сеть одной PostgreSQL-транзакцией.
2. **Импорт.** Есть определение формата, CSV/XLSX, GeoJSON, DXF, классификация слоёв, извлечение полилиний/точек/текста, импорт цифрового геологического PDF с обязательной ручной проверкой колонок.
3. **Трассировка.** Для водоснабжения сохранён эвристический генератор кольцевой сети. Для К1/К2 есть отдельный строгий конвейер с preflight, коридором, геопривязкой, препятствиями, дорогами, сетями, водой, штрафами рельефа и блокировками при неполноте данных.
4. **Расчёты.** Напорная сеть рассчитывается через `epanet-js`; самотёчная сеть — Manning, накопление расходов, подбор диаметра, скорости, заполнение, отметки и график профиля.
5. **Документация.** Есть векторные DXF/PDF, XLSX-ведомости, формы актов, пояснительная записка, ZIP и data-driven реестр планов, профилей, ведомостей, деталей и спецификаций.
6. **Контроль выпуска.** Листы имеют статусы `BLOCKED`, `PRELIMINARY`, `CALCULATED`, `VERIFIED`, `STALE`, источники и fingerprint. Отсутствующая ось, геопривязка, топография, классификация слоёв, геология, каталог или карточки пересечений блокируют зависимые листы.

Подробная матрица приведена в `current-capabilities.md`.

## Критические разрывы

### 1. Схема Supabase не имеет единственного надёжного пути развёртывания

`backend/migrations/0000_full_schema.sql` называется полной консолидированной схемой, но фактически содержит базовые таблицы из `0001` и инженерную сеть из `0012`. В нём отсутствуют таблицы/колонки миграций `0003`–`0011` и `0013`: каталоги, участки, существующие сети, реестр норм, регионы, геология, связь К1 с водным проектом, basis и каталог колодцев.

Одновременно `backend/README.md` предлагает выполнить только `0001_init.sql`, после чего современный frontend также будет обращаться к отсутствующим объектам. Последовательные миграции существуют, однако нет CLI-конфигурации, таблицы применённых версий, CI smoke-test или команды, подтверждающей production-схему. Это главный источник ошибок HTTP 400/404 при несовпадении frontend и Supabase.

### 2. Полный эталонный комплект на 61 страницу ещё не реализован

Текущий генератор намеренно data-driven:

- поддерживает шесть видов рабочих листов: `plan`, `network_plan`, `profile`, `material_table`, `detail`, `specification`;
- создаёт динамическое число листов основной серии, а спецификацию ведёт как отдельный `documentSet` с собственной нумерацией;
- добавляет три общие страницы PDF: титул, ведомость и source-driven общие данные;
- использует канонический пикетаж профиля при нарезке планов и не пересчитывает его по длине экранной полилинии;
- хранит явные диапазоны строк ведомостей и спецификаций и динамически пагинирует их;
- содержит отдельный сводный план подтверждённых полилиний сети без использования эталонной геометрии.

Добавлены нейтральный каталог 61 страницы, traceability matrix и 61 постраничный структурный контракт. Это правильная защита от подмены результата, но она пока не доказывает воспроизведение основной надписи, физического масштаба и оформления. Автоматический постраничный raster diff уже реализован, однако измеренной метрики на паре «реальный эталон — сгенерированный 61-листовый альбом» всё ещё нет.

### 3. Приёмочный benchmark пока не имеет полной пары PDF

`npm run benchmark` завершился с кодом 0, но сообщил об отсутствии локального приватного manifest и пропустил проверку. Для приёмки добавлены `npm run benchmark:required` и `npm run validate:release`: отсутствие manifest или полного результата там является ошибкой. `scripts/visual-benchmark.mjs` умеет одинаково рендерить два PDF, проверять количество страниц и MediaBox, считать RGB pixel/ink/structure score по каждому листу и сохранять JSON, HTML, Markdown и PNG-различия. Самотест на одинаковом девятистраничном PDF разрешён только с флагом `--self-test`; обычный режим отвергает одинаковые PDF. Поэтому текущего измеренного процента для R01 всё равно нет.

### 4. Converter не входит в корневую установку и локально не готов

`converter` не является npm workspace. После установленного корневого `node_modules` в `converter/node_modules` отсутствуют `express`, `cors`, `multer`; локальный `node src/index.js` завершается `ERR_MODULE_NOT_FOUND`. Dockerfile устанавливает зависимости отдельно и требует `ODA_DEB_URL`, поэтому deployment возможен, но в этом аудите реальная DWG↔DXF-конвертация не подтверждена. CloudConvert только объявлен и всегда возвращает `not implemented`.

### 5. Автоматическое чтение исходных документов неполно

- PDF обрабатывается только при наличии текстового слоя.
- OCR сканов отсутствует и явно отложен.
- Basis-файлы загружаются в Storage, но АПЗ, ТЗ, генплан, топосъёмка и итоговый альбом не проходят через единый извлекатель требований/геометрии.
- Нет общего реестра происхождения каждого значения вида `source/calculated/selected/user_confirmed/missing`.
- Нет автоматического анализа каждой страницы итогового альбома и связи «элемент листа → формула → норма → источник».

### 6. Нормативная база частично непроверена

В `NORM_REGISTRY` теперь 73 правила: 45 со статусом `verified`, 28 — `unverified`, у 16 отсутствует точный пункт (`clause: null`). Пять новых записей трассируют расчёт дождевого стока 5.8–5.13. В списке документов 12 отмечены verified и 8 unverified. Некоторые численные defaults всё ещё требуют подтверждения инженером.

### 7. Тестовый контур не покрывает production-интеграцию

Ядро хорошо покрыто unit-тестами, однако отсутствуют:

- E2E браузерный сценарий;
- тесты реального Supabase/RLS/Storage/RPC;
- round-trip тест реального DWG через ODA (unit-тесты fail-closed CORS converter уже добавлены);
- тесты полного импорта всех предоставленных файлов;
- OCR-тесты;
- постраничные raster/vector golden-тесты (61 структурный контракт уже есть, но он не измеряет визуальное сходство);
- coverage command и порог покрытия;
- lint command;
- приёмочный CI, который запускает существующую корневую команду `npm run test:all` вместе с typecheck, build и benchmark.

## Другие выявленные несоответствия

- `DrainageSection` и переводы продолжают сообщать, что K1 solver «в разработке», хотя `createGravitySolver('sewer')` и `GravitySection` уже подключены. Это устаревший текст интерфейса, а не отсутствие самого solver.
- `engine/src/systems.ts` описывает «light stubs», но объявляет все три solver как `ready`; комментарий устарел.
- `backend/README.md` не описывает современный порядок всех миграций.
- Ссылка на конкретное имя реального DWG в `docs/DEPLOY.md` заменена нейтральным описанием проектного файла.
- Тест геологии локально использует игнорируемый конфиденциальный файл и честно skip-ается в CI. В текущем запуске он выполнился, но проверяет лишь наличие распознаваемого текста/сводки, а не полноценные скважины и слои.

## Оценка текущей готовности

| Уровень | Оценка |
| --- | --- |
| Unit-ядро и production build | Работоспособны на проверенной машине |
| Синтетический проект | Существенная функциональность реализована; зависит от согласованной Supabase-схемы |
| Реальный DWG | Архитектура готова, но converter/ODA не подтверждён этим запуском |
| Реальный комплект К1/К2 | Частично: расчёты и динамические листы есть, полного доказанного E2E нет |
| 61 страница и сходство 99% | Структурный контракт и инструмент сравнения реализованы; реальное сходство не измерено и не подтверждено |
| Самостоятельная работа на произвольном новом проекте | Не подтверждена: отсутствуют универсальный ingestion, полная provenance-модель и E2E |

## Рекомендуемый порядок исправлений

1. Создать один канонический, полностью идемпотентный migration path и интеграционный schema-smoke-test.
2. Включить `converter` в воспроизводимую установку/CI и добавить health/ready/round-trip тест на малом DWG/DXF.
3. Расширить уже созданные source inventory, page catalog и traceability matrix до объектного lineage «элемент → формула → норма → источник».
4. Добавить OCR и структурированный импорт ТЗ/АПЗ/генплана/топосъёмки.
5. Довести динамическую модель листов до полного обязательного состава без фиксации количества в алгоритме.
6. Реализовать автоматическое рендер-сравнение каждой страницы и объективную scorecard.
7. Добавить E2E, Supabase, converter, mutation/anti-hardcoding и 61 визуальный golden-тест.
