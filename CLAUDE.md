# HydroPlan (AquaScheme) — правила для агентов

## Генеральный бенчмарк (приёмочный тест продукта)

Продукт принимается по схожести сгенерированного комплекта с эталонным
альбомом реального объекта: метрика в docs/benchmark/SCORECARD.md, цель ≥ 99%.
Правила:

1. Перед любым существенным изменением и в каждом PR прогоняется
   `npm run benchmark`. Падение score относительно последней записи журнала
   SCORECARD — блокер: изменение не мержится, пока score не восстановлен.
2. Данные бенчмарка конфиденциальны: docs/benchmark/ полностью в .gitignore.
   Данные реального объекта (адреса, организации, отметки, названия) НЕ
   переносить в демо-датасеты, примеры, скриншоты, тесты и коммиты.
3. Правило честности: если наш расчёт даёт другое, но допустимое по нормам
   решение, чем в эталоне, — не подгонять молча. Расхождение фиксируется в
   docs/benchmark/GAP.md (в эталоне X, у нас Y, обоснование обоих) и решается
   пользователем.
4. Каждое новое требование/функция проводится через docs/benchmark/REQUIREMENTS.md
   (какое требование ТЗ/АПЗ закрывает) и норм-реестр (документ, пункт, страница,
   редакция). Редакции норм для бенчмарк-проекта — указанные в ТЗ.
5. Нечитаемые или отсутствующие исходные данные не выдумываются — вопросом к
   пользователю (docs/benchmark/GAPS.md).

## Достижимость возможностей

Возможность не считается сделанной, пока к ней нет пути с экрана.

Движок развивается быстрее интерфейса и проверяется своими тестами: они
зелёные, а воспользоваться возможностью нельзя — вызывать её неоткуда. Так
накопились подбор насосов ЛНС, замок нормативных редакций, аудит происхождения
значений, вертикальная планировка, координаты скважин с чертежа, отбор
пересечений на вскрытие. Отдельный случай хуже обычной недоделки: шлюз выпуска
при этом остаётся недостижимым, и проект нельзя выпустить ни при каких данных
(так было с составом комплекта и с ролями слоёв на пути реконструкции).

Правила:

1. Новая функция движка сопровождается местом вызова: секция UI, конвейер или
   вход набора рабочих чертежей. Иначе она не мержится.
2. `npm run audit:reachability` считает экспортируемые функции движка, на
   которые нет ссылок извне их модуля, и сравнивает с уровнем в
   `docs/reachability-baseline.json`. Рост — блокер. Уровень может только
   снижаться; после снижения он записывается флагом `-- --write-baseline`.
3. У части позиций верное действие — не «подключить», а «перестать
   экспортировать»: внутренний помощник не должен лежать в публичной
   поверхности движка. Оба способа снижают уровень одинаково.
4. Прежде чем добавлять новую возможность, стоит проверить список: нужная
   может уже существовать и ждать подключения.

## Рабочие соглашения репозитория

- Нормативная база: docs/norms/ (PDF и txt вне git). Каждое инженерное решение
  обосновывается записью норм-реестра; неизвестный пункт = unverified, не выдумывать.
- Коммиты без Claude-трейлеров.
- vitest в этой среде: только `npx vitest run --pool=threads
  --poolOptions.threads.singleThread` (иначе OOM); при порче кэша удалить
  node_modules/.vite.
